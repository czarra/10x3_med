# Research: Edit / delete diary entry (S-06, FR-014)

**Date**: 2026-08-27T11:27:15+02:00
**Researcher**: Radoslaw Michałkiewicz
**Git Commit**: [`5504c76`](https://github.com/czarra/10x3_med/blob/5504c7673eb0e6510997c19d1592216b5110cb1c)
**Branch**: main
**Repository**: czarra/10x3_med

## Research Question

Roadmap slice **S-06** (`edit-delete-diary-entry`), PRD requirement **FR-014**: the patient should be able to edit or delete a diary entry they logged, but only within a limited recency window, so older entries stay locked to preserve analytics/trend consistency. What does the current codebase (`DiaryEntry` entity, `DiaryController`, forms, services, tests, security) already provide, what patterns should a plan reuse, and what's missing or ambiguous before this can be planned?

## Summary

The data foundation is already in place: `DiaryEntry` has an immutable `createdAt` timestamp stamped once at construction ([`src/Entity/DiaryEntry.php:53-54,63`](https://github.com/czarra/10x3_med/blob/5504c7673eb0e6510997c19d1592216b5110cb1c/src/Entity/DiaryEntry.php#L53-L63)) — the exact anchor FR-014's "within 24h of creation" needs, with no migration required. `DiaryEntryFormType` already excludes `user`, both snapshot fields, and `createdAt` from its editable field set, so it can be reused as-is for an edit form without risking corruption of immutable data.

However, this feature is a genuine "first" for the codebase in three ways: **no route in the app takes a resource `{id}` from the URL today**, **no ownership-check pattern exists** (`src/Security/` doesn't exist, no Voters anywhere), and **no delete action exists anywhere**. All three will be introduced for the first time by this change, so the plan should pick one consistent approach rather than improvise per-route.

There is also a real, unresolved **product ambiguity carried by the PRD itself**: FR-014's Polish wording ("np. ostatni wpis **lub** w ciągu 24h od utworzenia") and the roadmap's own two mentions of S-06 disagree with each other on whether "editable" means *only the single most-recent entry* or *any entry created in the last 24h regardless of position*. Neither `log-diary-entry` nor `diary-history-view`'s plans resolved this — they explicitly deferred it to this change (see Historical Context / Open Questions below). This should be nailed down before or during `/10x-plan`, ideally with the user, since it changes both the query shape and the UI (single "undo last entry" affordance vs. a per-row action column with per-row eligibility).

### Authorization / ownership — a gap this feature must fill first

- `src/Security/` does not exist. `grep -r "Voter" src/` → no results anywhere in the repo.
- All access control today is role-only (`#[IsGranted('ROLE_USER')]`) plus **implicit ownership by always looking up the resource scoped to the current user** rather than by a route `{id}` — e.g. `PatientProfileRepository::findOneByUser($user)` in [`ProfileController.php:24`](https://github.com/czarra/10x3_med/blob/5504c7673eb0e6510997c19d1592216b5110cb1c/src/Controller/ProfileController.php#L24).
- **No route anywhere in the app currently takes a resource `{id}` from the URL** (`grep -rn "{id}" src/Controller/` is empty). Editing/deleting a `DiaryEntry` by id will be the *first* place needing an explicit ownership check.
- Two idiomatic options, consistent with existing style:
  - **Repository-scoped lookup** (recommended, matches existing style): `findOneByIdAndUser(int $id, User $user): ?DiaryEntry`, then `createNotFoundException()` if null — directly mirrors the `null === $profile` pattern at `ProfileController.php:25-27` / `OnboardingController.php:26`.
  - A dedicated `DiaryEntryVoter` + `#[IsGranted('EDIT', subject: 'entry')]` — more idiomatic Symfony, but there is zero precedent for Voters in this repo, so it would be a bigger stylistic departure.
- No existing test covers "user A cannot touch user B's resource" — this is new test territory.

### Domain-service conventions to reuse

All services are `final class`, `src/Service/<Concept>/<Name>Service.php`, constructor-promoted `private readonly` dependencies, autowired (no manual service wiring — `config/services.yaml:19-20`).

- **Best pattern match for the 24h check**: [`GlucoseHistoryChartService::buildFor(User $user, \DateTimeImmutable $now)`](https://github.com/czarra/10x3_med/blob/5504c7673eb0e6510997c19d1592216b5110cb1c/src/Service/Chart/GlucoseHistoryChartService.php#L23) takes "now" as an **explicit parameter** rather than calling `new \DateTimeImmutable()` internally, and the controller supplies it at the call site (`DiaryController.php:70`). Tests then pass a fixed `$now` (`tests/Service/Chart/GlucoseHistoryChartServiceTest.php:19,36,39`). A new editability check should follow the same shape, e.g. `isEditable(DiaryEntry $entry, \DateTimeImmutable $now): bool`, to stay unit-testable without wall-clock flakiness.
- **Best pattern match for the result shape**: [`HypoglycemiaWarningService::evaluate(DiaryEntry $entry): HypoglycemiaWarningResult`](https://github.com/czarra/10x3_med/blob/5504c7673eb0e6510997c19d1592216b5110cb1c/src/Service/Warning/HypoglycemiaWarningService.php#L8-L38) — no constructor deps, `public const` thresholds, private-constructor DTO with `warn()`/`none()`-style factories. A binary "editable / not, with a reason" gate fits this shape well (e.g. `allowed()` / `deniedBecauseExpired()`).
- `InsulinWwRatioSuggestionService` (`src/Service/Suggestion/InsulinWwRatioSuggestionService.php:103-114`) shows the existing convention for "time window since an anchor timestamp" arithmetic via `getTimestamp()` diffs — a secondary reference if the 24h check needs anything beyond a simple `DateTimeImmutable::modify('+24 hours')` comparison.

### Validation conventions

- Field-level: `Assert\Range`, `Assert\LessThanOrEqual('now')` (used for `measuredAt`, not reusable for a *creation-relative* window like 24h-since-`createdAt` — that needs service-level logic, not a declarative constraint).
- Cross-field: class-level `#[Assert\Callback]` + method building violations via `buildViolation()->atPath()->addViolation()` (`DiaryEntry.php:163-176`).
- No `Assert\*` usage in any `Form` class — all validation lives on entities.

### Testing conventions

Full test tree: `tests/Controller/*`, `tests/Entity/*`, `tests/Kernel/KernelBootTest.php`, `tests/Service/{Chart,History,Suggestion,Warning}/*`.

- Controller tests: `WebTestCase`, `static::createClient()`, `$client->loginUser($user)`, form submission via `$crawler->filter('main > form')->form()` + `$form->setValues([...])` + `$client->submit($form)`. Real Postgres DB (`.env.test` → `database-test:5432/app_test`), **no transactions/fixtures** — each test creates its own user via `EntityManagerInterface` (unique email via `uniqid()`) and cleans up manually with raw SQL `DELETE` in a `finally` block (`tests/Controller/DiaryControllerTest.php:319-345`).
- Kernel-booted service tests (`DiaryHistoryServiceTest`, `GlucoseHistoryChartServiceTest`, `DiaryEntryTest`): `KernelTestCase` + `self::getContainer()->get(...)`.
- Pure-logic services with no DB dependency (`HypoglycemiaWarningServiceTest`): plain `PHPUnit\Framework\TestCase`, entities built directly with `new`.
- `phpunit.dist.xml` forces `APP_ENV=test`, `failOnDeprecation`/`failOnNotice`/`failOnWarning` all `true` — no precedent exists yet for an ownership-violation test ("user A can't touch user B's entry"); this will be new.

## Architecture Insights

- **Snapshots and `createdAt` are deliberately immutable** — no setters exist for `user`, `insulinWwRatioSnapshot`, `baseDoseSnapshot`, or `createdAt`. This is a design decision from S-02, not an oversight, and an edit flow should preserve it: editing corrects the six user-entered fields, never the ratio/dose snapshot captured at logging time or the original creation timestamp.
- **Time-as-parameter is the established testability convention** (`GlucoseHistoryChartService::buildFor($user, $now)`) — any new time-window logic (the 24h check) should follow this, not call `new \DateTimeImmutable()` internally, to stay unit-testable and match `HypoglycemiaWarningServiceTest`'s boundary-matrix testing style (just-below/at/just-above threshold).
- **Ownership is currently enforced by query shape, not by a generic authorization layer.** There is no Voter infrastructure in this app. Introducing one now would be a bigger architectural departure than extending the existing "look the resource up scoped to the current user" pattern with a new `findOneByIdAndUser()` repository method — consistent with `ProfileController`/`OnboardingController`.
- **Business-rule services are stateless and DTO-returning** (`HypoglycemiaWarningService`, and by extension a hypothetical editability service) — this repo doesn't reach for a shared "policy" or "specification" abstraction; each rule is its own small service.

## Open Questions

1. **Scope of the recency rule (the single biggest open item)**: does "editable" mean (a) only the chronologically last entry for the user, (b) any entry created within the last 24h regardless of position, or (c) the last entry *and* it must be within 24h (conjunction, per the roadmap summary table)? This changes the repository query, the editability service's signature, and the UI (one "undo last entry" affordance vs. a per-row gated action column). Recommend surfacing this explicitly to the user during `/10x-plan` rather than picking silently — the PRD and roadmap disagree with themselves.
2. **Ownership-check mechanism**: plain `findOneByIdAndUser()` + `createNotFoundException()` (matches existing `ProfileController`/`OnboardingController` style, zero new abstractions) vs. introducing the app's first Voter (`#[IsGranted('EDIT', subject: 'entry')]`, more idiomatic Symfony but a bigger departure). Research leans toward the repository-scoped lookup for consistency, but this is a plan-level decision.
3. **404 vs 403 for "exists but not editable / not yours"**: the codebase has no precedent distinguishing "doesn't exist" from "exists but forbidden" (everything today uses `createNotFoundException`). Decide whether an expired-window entry should look like a 404, a 403, or a disabled UI affordance with an explanatory message.
4. **Should edits be visibly marked** (e.g., an `updatedAt` column / "edited" badge)? Not required by the PRD text, no precedent in migrations — likely out of scope, but worth a one-line confirmation in the plan rather than silent omission.
5. **Delete confirmation UX**: no existing "destructive action" pattern (confirmation dialog, POST-only form with CSRF) exists anywhere in the app to copy from — this will be a new UI pattern, not just a new route.
6. **Downstream consistency**: FR-014's stated rationale is preserving "spójność danych analitycznych i trendów" (S-03's suggestion algorithm, S-05's chart both read historical `DiaryEntry` rows). Confirm whether edits/deletes within the 24h window need any interaction with `BaseDoseSuggestionService`/`InsulinWwRatioSuggestionService` (e.g., do they need to re-run or invalidate anything), or whether the 24h guardrail alone is considered sufficient protection — nothing in the PRD elaborates further, so this is worth a explicit yes/no in the plan rather than an assumption.

## Follow-up Research [2026-08-27T11:45:33+02:00]

### Trigger

Initial research (§ Open Questions 1 and 6) flagged the PRD/roadmap's internal ambiguity about editability scope, and flagged as unresolved whether edit/delete needed to interact with the suggestion-acceptance flow. The user then specified the actual product rule directly:

> Edycja/usunięcie wpisu z ostatnich 24h jest możliwa tylko jeśli w międzyczasie nie zaakceptowano na jego podstawie nowej dawki bazowej insuliny albo nowego przelicznika. Jeśli taka akcja już miała miejsce, dane są "odcięte" i nie można ich edytować. W przeciwnym razie — jeśli wpis nie został jeszcze odcięty — można go edytować/usuwać do 24h wstecz.

This sent me back into the live codebase, because the original three-agent sweep searched for the suggestion-acceptance flow by grepping `DiaryController` and the `Suggestion` services in isolation, and reported (incorrectly, as it turns out) that `BaseDoseSuggestionService`/`InsulinWwRatioSuggestionService` were "not currently wired into any controller." That miss meant the acceptance mechanism — which turns out to be exactly the "cutoff" concept the user describes — wasn't surfaced in the first pass.

### What was missed and now found

The acceptance flow lives in **`DashboardController`**, not `DiaryController`:

- [`src/Controller/DashboardController.php:42-83`](https://github.com/czarra/10x3_med/blob/5504c7673eb0e6510997c19d1592216b5110cb1c/src/Controller/DashboardController.php#L42-L83) — `acceptRatio()`: CSRF-checked POST action, re-runs `InsulinWwRatioSuggestionService::suggestFor()`, and if a suggestion is still available, updates `PatientProfile::insulinWwRatio` and persists a new `RatioAdjustmentHistory(user, oldRatio, newRatio, acceptedAt: new \DateTimeImmutable())`.

### Finalized editability rule

A `DiaryEntry` is editable/deletable if and only if **both** hold:

1. **Recency**: `now() - entry.getCreatedAt() <= 24 hours`.
2. **Not yet consumed by an accepted suggestion**: `entry.getMeasuredAt()` is strictly after **both**:
   - `ratioAdjustmentHistoryRepository->findLatestByUser($user)?->getAcceptedAt()` (or no history exists yet → treated as no lower bound), and
   - `baseDoseAdjustmentHistoryRepository->findLatestByUser($user)?->getAcceptedAt()` (same fallback).

   If either cutoff is `>= entry.getMeasuredAt()`, the entry is permanently locked from editing/deletion regardless of the 24h window (i.e., the 24h check becomes moot once an entry is "cut off" by either acceptance).

Confirmed with the user: the comparison field for the consumption check is `measuredAt` (not `createdAt`), for consistency with how both suggestion services already define their cutoff window — this was proposed and explicitly confirmed ("zgadzam się").

### Implications for planning

- This resolves **Open Question 1** (recency scope): the roadmap/PRD ambiguity between "last entry" vs "any entry within 24h" is moot — the real gating factor is the consumption check, not entry position. Any entry within 24h of `createdAt` is a *candidate*; the consumption check is what actually narrows it down (in practice, this will almost always coincide with "the most recent entries," since older entries are more likely to already be behind a cutoff — but the rule itself is not positional).
- This resolves **Open Question 6** (downstream consistency): yes, edit/delete does interact with the suggestion-acceptance flow, via a read-only check against existing `*AdjustmentHistory` cutoffs — no changes needed to the suggestion services themselves, no re-run/invalidation logic required, this is a one-directional guard.
- **New service candidate**: an editability-check service (e.g. `DiaryEntryEditabilityService::isEditable(DiaryEntry $entry, User $user, \DateTimeImmutable $now): bool` or a richer DTO à la `HypoglycemiaWarningResult`) should inject `DiaryEntryRepository`'s sibling repos — `RatioAdjustmentHistoryRepository` and `BaseDoseAdjustmentHistoryRepository` — the same two repositories already injected into the suggestion services, so no new repository methods are needed beyond the existing `findLatestByUser()`.
- **UI implication**: since eligibility is no longer purely "is this the last entry," the history view (`templates/diary/history.html.twig`) will need per-row eligibility evaluated against this service for every visible entry within the last 24h, not just the single latest row — reinforces the earlier finding that the "Actions" column must be per-row gated, not a single global affordance.
- **Correction to original research**: the statement that `BaseDoseSuggestionService`/`InsulinWwRatioSuggestionService` are "not currently wired into any controller" (original Detailed Findings, § Domain-service conventions) is **incorrect** — both are wired into `DashboardController` (`index()` for display, `acceptRatio()`/`acceptBaseDose()` for acceptance). Treat `DashboardController.php` as a required read for `/10x-plan`, alongside `DiaryController.php`.
